# OmniPOS web client

Offline-first POS in the browser. React 19 + Vite + IndexedDB, talking to the
Laravel API in `../omnipos-backend`.

---

## Running it

The backend must be up first:

```bash
cd ../omnipos-backend
php artisan serve
```

Then:

```bash
npm install
npm run dev
```

Opens on <http://localhost:5173>. Vite proxies `/api` and `/sanctum` to
`127.0.0.1:8000` so the Sanctum session cookie stays first-party — without that
proxy the cookie is cross-site and the session silently fails to stick.

Sign in with a seeded account (`php artisan db:seed` in the backend):

```
admin@omnipos.test    / password
manager@omnipos.test  / password
cashier@omnipos.test  / password
```

Other commands:

```bash
npm run typecheck
npm test
npm run build
```

## How offline works

On first sign-in the client downloads the catalogue and customers into
IndexedDB, then jumps its sync cursor to the server's current head. From that
point:

- **Reads** come from IndexedDB. Product search, the category rail, the customer
  lookup and the orders list never touch the network.
- **Writes** go to IndexedDB and queue an operation in an outbox table.
- **The sync engine** pushes the outbox and pulls the changefeed when a
  connection is available — on reconnect, on tab focus, and on a slow timer.

A sale completes identically whether the shop is online or not. The only
difference is how long the operation waits in the outbox.

The service worker precaches the app shell so the till opens with no network at
all. It deliberately does **not** cache API responses: offline reads come from a
real database the sync engine maintains, and a stale HTTP cache pretending to be
data would silently disagree with it.

## Three things worth understanding before changing this

### 1. Money is integers, everywhere

`src/features/pos/cart.ts` works in minor units (pesewas, cents) and converts to
a decimal string only at the edges. JavaScript cannot represent `0.1` exactly, so
accumulating floats across a basket produces totals that are a penny out — which
on a till is the difference between a drawer that balances and one that does not.

`toMinor` / `toDecimal` are the only conversion points. Adding a float path
anywhere in the cart reintroduces the bug.

### 2. Every write carries an idempotency key that never changes

`enqueue()` in `src/sync/engine.ts` generates an `operation_id` once, at the
moment of the local write, and the retry path reuses it untouched.

If the connection drops after the server commits but before the response
arrives, the client cannot know whether the sale landed — so it retries. The
server recognises the same `operation_id` and answers from the stored result
instead of booking a second sale. Regenerating that id on retry would turn every
flaky connection into duplicate revenue.

A `duplicate` response is therefore treated as success, not as an error.

### 3. Conflicts are kept and settled, never dropped

An operation the server refuses is marked `conflict`, stays in the outbox, and
surfaces on the Sync screen with the sale attached — amount, lines, time,
customer — because a reason string alone is not enough to decide.

A manager (not a cashier) can then:

- **Re-issue under a new receipt number** — the usual case. Two offline tills
  both reached the same number and *both sales are real*, so neither may be
  thrown away.
- **Try again as-is** — the cause was circumstantial, e.g. a product another
  till deleted and has since restored.
- **Discard** — a genuine double entry. The sale stays on the device, marked
  `discarded`, because someone took money against it and may hold a receipt.

**The rule `src/sync/resolve.ts` exists to enforce: every resolution that
re-pushes mints a NEW `operation_id`.** The server records every operation_id it
has seen, rejections included. Re-pushing a corrected payload under the original
id hits the idempotency short-circuit — the server answers `duplicate` from the
stored conflict result, applies nothing, and the client deletes the outbox row
believing it succeeded. The sale would vanish while looking like success. That is
the worst failure this system can produce, and it is one line away.

Re-issue asks the server for the next free receipt number
(`GET /api/orders/next-number`) rather than deriving one locally. Local knowledge
is exactly what was wrong: an offline till does not know which numbers the other
tills consumed, so a local guess collides again, once per attempt.

## Icons

Brand assets live in `public/`, generated by favicon.io from the OmniPOS mark:
`favicon.ico`, 16/32px PNGs, `apple-touch-icon.png`, and the 192/512 PNGs the
web app manifest points at. All are precached by the service worker so an
installed till shows its icon offline.

The manifest declares `purpose: "any"` only. The mark is edge-to-edge on a
transparent canvas with no safe-zone padding, so declaring it `maskable` would
let Android crop the blue arc. A maskable variant needs its own padded artwork
rather than a reuse of these files.

## Why this does not reuse the mobile core

The earlier plan was to share `src/core`, `src/database` and `src/sync` from the
mobile repo. For the platform seam and the id generator that reasoning still
holds. **For the sync engine it turned out not to be available:** the mobile
engine has ~20 Supabase call sites and is bound to that transport, so it cannot
speak to Laravel without being rewritten.

So `src/sync/engine.ts` here is the **canonical client for the OmniPOS sync
protocol**. When the mobile app is repointed at Laravel it should adopt this
implementation rather than growing a second one — two implementations of the
money path is exactly the divergence the architecture exists to avoid.

`core/uuidv7.ts` is deliberately behaviour-identical to the mobile
`src/core/ids/uuidv7.ts` for the same reason.

## The drawer, returns, receipts and catalogue writes

All four are local-first, for the same reason sales are. A shop with no
connection still counts its float at eight in the morning, still takes goods back
over the counter, and still hands the customer a receipt.

**The drawer** (`/shift`) opens against a counted float, records cash in and out
during the shift, and closes against a counted amount. The variance is recorded,
never corrected: a till that quietly adjusts its own expected figure to match the
count cannot detect either theft or error, which is the only reason to count.

Only cash is counted. Card and transfer never reach the box, so including them
would leave every honest drawer looking short by the day's card takings.

The client and the server compute expected cash by different routes and must
agree. The client counts sales and subtracts refunds; the server sums a payments
ledger in which refunds are already negative rows, so it does **not** subtract
them again. Subtracting twice on either side makes an honest till look short by
exactly the day's refunds. Both sides are pinned by tests, and the agreement was
checked against a live server: GHS 200 float, GHS 16 cash sale, GHS 8 cash
refund, GHS 15 paid out — both arrived at GHS 193.00 independently.

**A sale without an open drawer is warned about, not blocked.** Refusing to trade
over a bookkeeping detail is worse than an unattributed sale: one is recoverable,
a queue of turned-away customers is not.

**Returns** (`/returns`) look the sale up by receipt number — locally first, then
from the server, so a customer can be refunded at a till that did not serve them.
Eligibility comes from the server whenever there is a connection, because this
till only knows the refunds it processed itself and two terminals refunding the
same items is how a shop pays out twice. Offline, the screen says plainly that
its figures are local and the server may still reject.

**Receipts** (`/receipt/:id`) render from the local order and print through the
browser, so they work while the sale is still in the outbox. A sale that has not
reached the server prints saying so — the cashier handing it over during an
outage should be able to see that, and so should whoever reconciles it later.

**Catalogue writes** are on Inventory and Customers. Products are admin/manager
only, matching what the server's handler will accept. Stock is never sent as an
attribute: a new product starts at zero and its opening count is a separate
movement, because an absolute figure from a device that synced late would erase
another till's sales.

**Multi-store switching** appears in the header only for someone who belongs to
more than one store.

## Settling a customer's account

Both clients could put a customer into debt and neither could take them out of
it. Debt only ever grew.

Settlements go through the sync queue rather than the REST endpoint, because
taking cash across a counter cannot depend on a connection. They are cash in the
drawer, so they reach the reconciliation — but as their own line, never folded
into sales. A debt paid today is money in the box; it is not trade done today,
and adding it to the day's takings would report business the shop never did.

Overpayment is refused rather than held as credit. It is almost always a typo at
a counter, and the money is easier to hand back now than to explain on a
statement later.

## Settings, staff and reports

Settings is deliberately online-only and says so when it cannot reach the server.
Nobody changes a VAT rate mid-queue, and queueing it offline would let two
managers set different rates on different devices with no way to tell which was
meant. Selling, returns and the drawer keep working regardless.

The staff rules live on the server and are only reflected in the UI — a manager
cannot mint an admin, and the last admin cannot be removed or demoted. A shop
must not be able to lock itself out from a device with a stale idea of who else
is an admin.

Reports cover every till, which is why every figure comes from the server. The
profit report names its revenue line "revenue with known cost", because lines
sold before a cost price was recorded are excluded from both sides — the margin
is accurate for what it covers and covers less of the business than a bare
"revenue" would imply.

## Verified end to end

Run against a live backend on 2026-08-31: login, catalogue bootstrap, online
sale, backend killed mid-session, offline sale, backend restarted, queue drained.
Server-side afterwards: correct totals, `client_created_at` preserved on the
offline sale, zero conflicts, and every product's cached stock exactly equal to
its movement ledger.

Idempotency was proven directly rather than assumed: the same `operation_id`
pushed twice produced one order, one payment and one changefeed entry, with the
second attempt answered `duplicate`.

Four defects were found and fixed during that run:

1. **`SESSION_DOMAIN=localhost`** pinned the session cookie to one hostname, so
   the app failed with "CSRF token mismatch" on `127.0.0.1`. Now `null`.
2. **Web sign-out always returned 500.** `currentAccessToken()` returns a
   `TransientToken` (truthy, no `delete()`) for cookie sessions. Because the
   client signs out locally regardless, the cashier appeared signed out while the
   server session stayed live.
3. **A failed local wipe left the till half-signed-out.** Dexie loses its
   transaction context across `Promise.all`, so `clearLocalData()` threw
   part-way and the state update never ran. Sign-out now applies the
   signed-out state first and treats everything after it as best-effort.
4. **"Remove" on a cart line was clipped to "Rem"**, because the icon-button rule
   sized every button in the row to 1.8rem. A cashier could not take a mis-scanned
   item off the sale.

## Multi-device conflict, verified

Two tills, both offline, both issuing receipt OM-20260831-0001. Driven for real:
the second till's push was rejected, and afterwards

- the first till's sale was untouched (still 28.00, 2 items, one row with that
  number) — no silent overwrite;
- **no stock moved** for the rejected sale, and the ledger still matched every
  cached quantity exactly;
- revenue was unchanged;
- the conflict was recorded server-side with BOTH the client payload and the
  server state, so a human can see what each till believed;
- the operation moved to `conflict` and stopped retrying, rather than looping;
- the sale stayed in the till's local database and remained reprintable, because
  the customer is holding a paper receipt for it.

The rejection happens before any write commits, which is why nothing leaked.

## A session note that matters offline

`SESSION_LIFETIME` is 120 minutes. If the server session expires while a till is
disconnected, queued sales are **not** lost — they sit in the outbox and survive
re-authentication — but somebody has to sign in again before the queue can drain.
A shop that opens offline after a long closure will hit this. Consider a longer
lifetime for till devices, or the mobile bearer-token flow, which does not expire
the same way.

## Conflict resolution, verified

Driven end to end: two tills issued OM-…-0001, the second was rejected, and a
manager re-issued it from the Sync screen. Afterwards the re-issued sale was
booked as a new number, **the first till's sale was untouched**, both sales
survived, stock drift was zero, and revenue still reconciled against payments
plus customer debt. The decision was written to `audit_logs`.

Two bugs surfaced only in that live run and are fixed:

1. **Re-issue derived the next number locally** and collided again — twice —
   because the till had no idea which numbers other tills had used. It now asks
   the server.
2. **`GET /api/orders/next-number` returned a number already taken.** Casting the
   suffix inside SQL with a bound offset silently produced null. It now takes the
   lexical max, which is also the numeric max because the suffix is zero-padded.

## Settling another till's conflict

The Sync screen has two sections, and the difference is not cosmetic.

**Needs a decision** — conflicts this device raised. The corrected sale is in
local IndexedDB, so the client fixes it and re-pushes under a fresh
`operation_id`.

**Other tills** — conflicts raised anywhere in the store. The manager never had
that sale, so the correction cannot come from their device. `POST
/api/sync/conflicts/{operationId}/resolve` with `action: "reissue"` re-applies
the payload the server kept when the push was rejected, under a receipt number
the server knows is free. It runs through the same entity handler a push would,
so there is still one implementation of the money path.

The originating till does not need to be reachable. When it next syncs, the sale
arrives through the changefeed — published with `origin_device_id: null` so every
till receives it, including the one that raised the conflict — and the client
adopts the server's receipt number and clears its own conflict. Without that last
step a till would keep asking for a decision about a sale already on the books,
and a second manager could settle it twice.

`acknowledge` is a distinct action from `reissue` for the same reason: when the
originating till has already fixed and re-pushed the sale itself, the server must
mark the row settled **without** applying the stored payload, or the same sale is
booked twice.

Verified live: a manager booked two other tills' sales as `0007` and `0008`,
payments carried across, the numbers already held were untouched, stock drift
stayed zero, and the books reconciled. Each decision is in `audit_logs` with the
number it was booked as.

## Service worker: what is checked, and what is not

`src/test/precache.test.ts` runs against the real `dist/` output on every test
run and asserts:

- every asset `index.html` references is in the precache manifest;
- `index.html` itself is cached and a `NavigationRoute` is bound to it, so an
  offline navigation resolves to the shell;
- **no API response is precached** — offline reads come from IndexedDB, which the
  sync engine reconciles. An HTTP cache of the same data would be a second, stale
  copy that nothing reconciles, and no way to tell which was right;
- the icons are cached, so an installed till shows its branding offline.

The test was verified to fail: removing the stylesheet from the manifest makes it
report that exact file. That is the realistic regression — a `globPatterns`
change that quietly stops matching something, which every other test would still
pass because everything works while the network is up.

The built shell has no external runtime dependency (702 KB, all same-origin), so
once cached it is genuinely self-sufficient.

**A true cold offline start has NOT been executed.** Service worker registration
is blocked in the browser available here — a two-line worker with no imports
fails to register identically to the real one, so it is the environment, not the
app. Confirming that the shell actually serves from cache with the origin server
gone needs a normal browser:

1. `npm run build && npm run preview`
2. Load <http://127.0.0.1:4173>, sign in, let the catalogue download
3. Confirm a service worker is active in DevTools → Application
4. Stop the preview server **and** the backend
5. Reload — the app should open and the POS should still sell from IndexedDB

Everything behind the shell is already proven offline: sales complete, queue, and
survive reconnection with both servers stopped.
